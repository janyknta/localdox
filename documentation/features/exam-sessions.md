# Exam Workspaces

Exam Workspaces are a workspace kind in the core Localdox application. Create one in **Settings > Workspace > New**, choose **Exam Workspace**, and open it from the shared workspace switcher. Existing document workspaces default to Reader Workspace. Documentation Workspace is reserved in the feature registry and shown as coming later.

An Exam Workspace looks and works exactly like every other workspace: the same sidebar, files, folders, header and footer. Learners organise it themselves. An exam is a `.xam` paper (questions, keys and solutions) governed by an `.xrule` (time, pass mark, attempts, marking). The `.xrule` either sits beside the paper with the same name, or is the one rules file in a folder above it, which then covers every paper in that folder. Opening a `.xam` in an Exam Workspace shows its rules, one action (start, resume, retake or review) and its attempts in place of the document; the instructions and the timed exam cover the screen while it runs, and the result, with every answer and solution, then sits in the reader. In other workspaces the same file previews its questions, never its keys. Practice is a separate `.xp` file that opens in any workspace and checks each answer the moment it is given. Formats, rules lookup and how progress follows edits: see [Exam files](exam-files.md).

The `/exams` URL remains a compatibility entry into the core shell. Old exam records are assigned to one stable legacy Exam Workspace without rewriting the records or progress; records made by the earlier exam screens (variations, exam types, library exams) have no files, so they are listed and deleted in Settings rather than shown in the workspace. Each paper's plan is keyed by its file id. Plans and attempts use compound workspace/id keys in feature stores; recovery journals and browser writer locks are scoped to the workspace. Imported author IDs can repeat in different workspaces safely. Settings lists uploaded exam data across all workspaces, and deleting a workspace removes its exam data as well as materials. The document workspace JSON export currently covers materials and annotations; exam data remains in its feature stores and this limitation is stated in Settings.

An exam's flow is `files → validation → instructions → timed session → sealed submission → scoring → result → answer review`. The engine can also run confidence reflection and rule-based diagnostics; the UI skips reflection and shows no analytics (learners judge their own mistakes from the key and solutions), but the engine and its tests are kept. The engine never identifies an exam by name. `schema.ts`, `parser.ts` and `validation.ts` establish the file boundary; `session.ts` replays events and enforces deadlines/navigation; `scoring.ts` applies question-type policies; `diagnostics.ts` interprets the rule data and aggregates evidence. These modules have no UI dependencies.

`storage.ts` owns a separate IndexedDB database and refuses to read solutions before submission. Imported keys remain opaque Blobs; bundled keys are non-inlined assets fetched only after the submission is persisted. The browser lock serializes writers across tabs. A synchronous localStorage recovery journal holds pending response/progress snapshots until their IndexedDB writes commit; startup restores unfinished writes before resuming. Paper and solution content never enters that journal. A storage error is visible and blocks further answer changes until saving succeeds. Reimporting content does not rewrite the exam snapshot held by an existing attempt.

The UI uses its own small token layer (below), Radix Dialog, KaTeX, Mermaid and Recharts. Exam Markdown deliberately does not execute the reader's interactive React/code fences, and the scientific calculator executes no JavaScript strings.

The main tradeoff is the conflicting solution-validation timing: keys cannot be checked before starting without reading them. Validation is deferred until after submission, and a malformed/missing key leaves a retryable locked submission. There is no pretense of server-backed secrecy or tamper-proof proctoring in a local Markdown reader.

For the complete engine ruleset (an `.xrule`'s `rules` block), diagnostics semantics and checks, see [Exam format](../docs/exam-format.md). To try the flow, create `example.xam` with **New file** in an Exam Workspace and choose **Create example.xrule**.

## A paper's plan: the exam's ledger

**The problem.** Papers used to carry four gated steps (Learn → Practice → Exam → Review) and a `# Practice` part. That mixed two jobs with opposite rules in one file: an exam must hide its keys until it is submitted, while practice exists to show them at once. It also put a self-reported Learn step and a practice quota between a learner and the exam they came to sit.

**The model.** An `.xam` is only an exam, and practice lives in `.xp` files (see [Exam files](exam-files.md)). Each paper still has one study-plan record (`study-plan.ts`), but it is now the exam's ledger, not a stepper: the paper versions it was given (`cycles`), the attempts linked to them, and from those `studyProgress` derives one status: `ready`, `in_progress`, `failed`, `revision_required` or `passed`. `ExamPanel.tsx` shows one action per status. A passed paper is final; its review stays open.

**Data flow.** The plan is built from the `.xam` and `.xrule` by `paper-plan.ts` (`syncPaperPlan`), with images resolved from the workspace by file name. It snapshots the exam, so editing a file after an attempt never rewrites progress (the plan is pinned).

**Retries.** A failed attempt can be retaken while attempts remain. Exhausting `attempts.max` needs a different qualifying paper: new questions, at least the rule's share tagged with its difficulty label, same pass mark and limit. **Use the edited paper** records the revision and attaches the file's current questions in one action. Content fingerprints ignore renamed IDs, shuffled ordering and whitespace, so superficial edits do not reset the limit.

**Storage.** Plans live in the `plans` IndexedDB store. All writes use the same exclusive browser lock and serialized save queue, and the recovery journal covers plan edits (revision, the legacy checklist and notes) as well as attempts. Plans imported by the earlier study-plan screens still load; their tasks and notes are kept, but nothing shows or gates on them now.

## Interface: a calm exam platform

**The problem.** A practice tool only builds exam temperament if it feels like the real thing. GATE (TCS iON) and JEE (NTA) candidates expect a fixed layout: timer top-right, section tabs, a question palette whose shapes mean something, and a sticky action bar. Anything extra, such as internal IDs, validation reports or banners that move the question, costs attention during a timed sitting.

**The rule that shapes everything.** The UI only presents. `session.ts`, `scoring.ts`, `diagnostics.ts` and `study-plan.ts` decide; the screens never re-derive a grade, a deadline or an unlock. Data additions are all optional with safe defaults: the ruleset's `ui` block (`profile`, `kind`) and a session's `timeScale` (scaled time for short samples).

**Decisions worth knowing before you change them.**

- _One notice slot._ Timer thresholds, integrity warnings, pause and expiry all share one fixed-height slot beside the question number (inside the sticky action bar on phones). Nothing above the question changes height, so the question never jumps. Priority: paused → time's up → fullscreen off → recent warning → threshold.
- _Thresholds fire once, briefly._ A threshold at or above the clock's length is dropped (a 10-minute exam never says "10 minutes left" at the start). A crossed threshold shows for 10 seconds; the timer colour carries it after that (amber after the first, red after the last). Because this is derived from remaining time, a resumed attempt doesn't replay old warnings.
- _Percentages round down._ `formatPercent(79.6)` is `79%`, so a failed 80% gate can never display "80%".
- _No exam sidebar._ The reader's sidebar is the navigation. A paper is a file, so selection, history, the mobile drawer and reload restore all come from the reader.
- _One action per state._ The paper shows a single primary button for where the learner stands (Start, Resume, Retake, Review answers, or Use the edited paper), with past attempts listed beneath. There is nothing to unlock first.
- _Exam diagrams are strict and static._ Exam files may come from anyone, so `ExamMarkdown` calls Mermaid with `securityLevel: "strict"` and no reader chrome, instead of the reader's `MermaidBlock` (which uses `loose` for the user's own documents). Diagram and chart fences render outside the code container.
- _Images are resolved, not fetched blindly._ `ExamAssets` maps file names to object URLs (inferring the MIME type, without which browsers won't draw an SVG blob). Only shipped files, `https:` and `data:image` sources load, always through `<img>`.
- _Import errors are sentences._ `describeImportIssues` turns schema issues into "file, line N: what to fix", for learners and for pasting back to the GPT.
- _Instructions is mandatory._ "Start" creates an attempt and opens the instructions page (the acknowledgement is part of the engine).
- _Author material is behind `?dev=1`._ Rule IDs, impact scores, question IDs in review and the event log are hidden from learners. File errors still show: the learner is the author of their files.
- _Dialogs sit above everything._ `Dialog` portals into the fullscreen element when one exists (see `use-portal-container`), so confirms remain visible during a fullscreen exam.

- _One result screen, in the reader._ `ResultScreen` shows the score, sections and then **Answers & solutions**: an outcome map (one numbered cell per question, coloured and labelled correct / wrong / partly / not answered) that jumps to the question, a Mistakes / All filter, and each question with its key and solution. Result and review used to be two full-screen pages, so checking a mistake meant leaving the score, and the sidebar vanished for no reason once the clock had stopped. Only the timed part needs the exam hall. The engine's `submitted` and `review` phases are kept (attempts store them); `review` now only means "open at the answers".

## Saving answers the TCS iON way (`navigation.requireSave`)

**The problem.** In a GATE hall (TCS iON), choosing an option doesn't record it. An answer counts only after **Save & next** or **Mark for review & next**; clicking a palette number, a section tab or Previous leaves the question and silently drops the choice. Candidates who practise on a tool that saves on click lose marks on the day.

**The model.** Think of the question screen as a form with a draft. The draft is what is on screen; the saved answer is what the palette, the submit summary and grading see. `ExamScreen` holds the draft (`draft`, keyed to the question it belongs to, cleared whenever `session.currentId` changes). Save & next and Mark for review & next call `onSave(response, { mark, nextId })`, which `ExamApp` applies as one `update`: `setAnswer` if it changed, `markQuestion` if the mark changed, then `navigate`, persisted together. The session engine is unchanged: it still records only answers it is given, so a draft can never reach grading.

**Rules that follow TCS iON:** Save & next on a marked question removes the mark (the status follows the last button pressed); Mark for review & next always marks; clicking a chosen MCQ option again deselects it; Clear response clears the draft and the saved answer; on the last question Save & next saves and stays. Time running out submits saved answers only.

**Guards the real exam lacks.** The notice slot says "Not saved. Save & next keeps this answer." while a draft differs from the saved answer, and the submit dialog names a question whose choice isn't saved. The instructions page explains the rule in an "Answering a question" list built from the rules (`answeringSteps`). These warn; they never save on the learner's behalf.

**Other TCS iON details.** The submit dialog's table has one column per palette state (Answered, Not answered, Marked for review, Answered & marked, Not visited) plus the question count, so the columns add up. **Instructions** and **Question paper** in the side panel reopen the rules and list every question read-only. Going to a question from the paper leaves the current one, like the palette.

**Off by default.** Generic rulesets keep save-on-choose, which suits short quizzes; the GATE preset turns it on. Attempts snapshot their ruleset, so changing the preset never changes an attempt in progress.

**Debugging.** If text is mis-coloured, check specificity: element defaults use `:where()` so any `ex-` class wins. If a dialog or menu is unstyled, it is missing the `ex-portal` class that carries the tokens outside `.exam-app`. Charts use `var(--ex-…)` in SVG attributes, which modern browsers resolve.
